# Decisions

The "why" log. Each entry has the choice, the reason and what it costs.

## 1. TypeScript end to end for v1
**Choice.** The server, console, contract and reporter are all TypeScript in one pnpm workspace; the implementation plan had Go for the server.
**Why.** One typed contract (`@tessera/contract`) is imported by all three, so a schema change breaks the build in every place at once instead of being discovered at runtime. A single language lets a small team own the whole system.
**Cost.** No single static binary yet. A Go ingest edge remains the plan when fan-in volume calls for it; the contract is the seam.

## 2. Claude Code hooks, not a plugin, for the first reporter
**Choice.** The reporter is a Node script driven by Claude Code's settings hooks; token usage is read from the session's JSONL transcript.
**Why.** Hooks are documented, stable and work for every install, including managed ones; the plugin API is newer and changes faster. The transcript carries exact per-request usage and model ids.
**Cost.** No status line inside the session, no per-step effort, and permission prompts can only be answered while the `PermissionRequest` hook waits (55 s by default) before Claude Code's own dialog takes over.

## 3. Snapshot plus unacknowledged events on the wire
**Choice.** Every report is the whole session plus the events the server has not acknowledged.
**Why.** A lost, duplicated or re-ordered report cannot corrupt state; a restarted server recovers from the next report.
**Cost.** Larger reports; at one per hook call that is fine.

## 4. PostgreSQL for everything, Redis optional
**Choice.** Sessions, agents, events, per-second samples, asks, deliveries and the audit log are all in PostgreSQL. Redis is only for fan-out across replicas.
**Why.** One durable store a platform team already runs; row-level tenancy by `org_id`; no second system until the samples table says so.
**Cost.** Per-second samples at thousands of sessions will outgrow a single table; the plan's ClickHouse tier is the next step and the `samples` table is the only part that moves.

## 5. Identity from the device token, never from the payload
**Choice.** A report is accepted only with a device token; the owner is the token's user. A session that already belongs to another user is refused (409).
**Why.** A name in a payload can be typed by anyone.
**Cost.** A machine shared by two people needs two config directories (`TESSERA_HOME`).

## 6. Cost priced on read
**Choice.** Tokens per model are stored; dollars are computed when read with the organisation's price table laid over the built-in list prices. A model with no price is shown as unpriced, never as zero.
**Why.** A contracted-rate change must move every figure at once, and an invented number is worse than none.
**Cost.** Budget spend uses the cost recorded in each sample at ingest time, so a price change does not re-open a closed budget window.

## 7. Enforcement through the PreToolUse hook
**Choice.** A hard budget with enforcement, or a paused session, denies new tool calls with a reason the engineer sees in the terminal. Tessera never kills a process.
**Why.** It is the strongest action a hook can take without reaching into the machine, and it is reversible from the console.
**Cost.** The model keeps its context and can keep thinking; only tool use stops.

## 8. Append-only, hash-chained audit with canonical JSON
**Choice.** Every mutation writes an audit row whose hash covers canonical JSON of its content and the previous row's hash.
**Why.** An auditor can verify the log was not edited. Canonical JSON because `jsonb` does not preserve key order (found by the first chain verification).
**Cost.** One extra `SELECT` per mutation to fetch the previous hash; audit writes within an org are serialised by that order.

## 9. Reporter writes use synchronous_commit off
**Choice.** The ingest path has its own Postgres pool whose connections run with `synchronous_commit = off`. Everything else (sign-in, answers to sessions, budgets, audit) keeps full durability.
**Why.** A report is a full snapshot that the reporter sends again a second later, so losing the last fraction of a second of reports in a database crash loses nothing the next report does not restore. It removes a WAL flush from every report, and the separate pool means a burst of reports never makes the console wait for a connection.
**Cost.** Activity events in the lost window can be gone for good, because the reporter dropped them after the acknowledgement. They are short activity lines, not audit records.

## 10. Live counts on the wall come from the session list, not the KPI tick
**Choice.** Live sessions, waiting sessions and running agents shown on the wall are counted in the browser from the same session list the filters and cards use. The server's KPIs supply only figures that need the database (cost today, tokens per minute, blowouts).
**Why.** The two sources update on different clocks (500 ms batches and a 2 s tick), so the same screen showed three different "waiting" numbers under load.
**Cost.** None worth noting; the server still computes the live counts for API clients.

## 11. Motion on the wall is reserved for what needs attention
**Choice.** Running-agent squares are static; only the top-bar live dot and the ring around a waiting card animate, and both animate opacity on their own layer.
**Why.** A wall of a hundred pulsing squares cost a third of the browser's main thread at 500 sessions and drowned out the one signal that matters: a session waiting on someone.
**Cost.** A running agent is shown by colour and the "N agents working" line rather than by movement.

## 12. Single sign-on is OIDC first, bound to the provider's subject
**Choice.** SSO is OpenID Connect (authorization code with PKCE, ID tokens checked against the provider's JWKS), one provider per organisation, routed by email domain. SAML waits until a customer needs it.
**Why.** Okta, Entra ID, Google Workspace, Auth0 and Keycloak all speak OIDC, and it needs no XML signature handling, which is where SAML implementations usually go wrong.
**Safeguards.** A provider signs in only users of its own organisation, so a misconfigured or hostile provider cannot assert someone else's email into another org. The first SSO sign-in binds the user to the provider's (issuer, subject); after that, an identity with the same email but a different subject is refused, so re-using an email at the provider does not take over an account (an owner can unlink). Only owners change SSO settings, so an admin cannot point the org at a provider that impersonates an owner. Public email domains cannot be claimed, and a domain belongs to one organisation. Requiring SSO leaves owners their password as a way back in when the provider is down.
**Cost.** Resolved by decision 19: domains are verified with DNS, and SCIM deactivates people removed at the provider.

## 13. Answering from Slack is the console's answer, made by a person Slack vouches for
**Choice.** Slack buttons call the same `answerAsk` path as the console: the session must be live, the prompt still open, and the person allowed to act on the session. The Slack user is matched to a Tessera user by the email Slack holds for them, in the channel's organisation only, and the match is remembered per Slack workspace and user. Every request is checked against the app's signing secret and a five-minute timestamp window before anything in it is read as an instruction.
**Why.** A second, weaker way to approve a tool call would undo the rules the console enforces. Email is the one identifier both systems already agree on, and Slack verifies it.
**Cost.** Someone whose Slack email differs from their Tessera email cannot answer from Slack until an admin fixes one of them; they are told so privately. Each organisation brings its own Slack app (a manifest is provided) rather than installing a shared one, so there is no OAuth install flow to run, and no Tessera-operated app holds tokens for many companies.

## 14. Notifications close themselves
**Choice.** When a waiting prompt is answered (anywhere) or the session moves on, Tessera edits its Slack messages to remove the buttons and say who answered, and resolves its PagerDuty incident. Channels can wait before notifying, so a team-lead or on-call channel only hears about sessions still waiting after, say, fifteen minutes.
**Why.** Stale buttons invite a second answer to a question that is gone, and an incident nobody resolves teaches people to ignore the pager.
**Cost.** Waiting state is held in the server's memory; a restart re-notifies channels with a delay about prompts that were already waiting (the notification log stops a channel being told twice about the same prompt).

## 15. Policy rules are ordered globs, checked on the server before every tool call
**Choice.** A policy is an ordered list of rules; the first enabled, enforcing rule that matches a tool call decides it (deny, ask, or allow), and a call no rule matches goes ahead. Conditions are globs over the tool, command, paths, URL, model, repository, branch and team, never regular expressions. Rules can run as a dry run, which records what they would have done. Every save is a new version; a save based on an older version is refused.
**Why.** First-match-wins is how firewalls and CODEOWNERS read, so an `allow` above a broader `deny` is an exception anyone can follow. Globs cover what people write ("terraform apply*", "**/.env") and are matched by a bounded dynamic programme, so no rule can take super-linear time on a long command, which a user-supplied regular expression could. "Ask" forces Claude Code's permission prompt, which Tessera already routes to the wall and to Slack, so approval needs no new mechanism. The reporter sends the command, paths and URL redacted on the machine, so a policy check never moves a secret.
**Cost.** Rules guard against mistakes, not adversaries: a command can be phrased so a glob does not see it. If a machine cannot reach Tessera within 1.5 s, the call goes ahead (fail open), so an outage of Tessera never stops engineers working. OPA/Rego, which the plan named, is not used: it would add a second language and a sidecar for what globs already express; the rule format can be compiled to Rego later if a customer needs it.

## 16. Stop ends the turn, not the process; hand-over adds a person, not an owner
**Choice.** Stop is a one-shot request: the session's next tool call is refused with `continue: false`, so Claude ends its turn and the engineer gets the terminal back. A stop that never meets a tool call lapses when the turn ends. Hand-over records an assignee next to the owner; the assignee is notified and may act, the owner keeps every right, and reports still come from the owner's device.
**Why.** Tessera never connects to an engineer's machine, so it cannot kill a process, and should not: stopping the agent's work is what people need, and the engineer decides what happens next. Ownership is tied to the device token that reports the session; moving it would let one person's machine report as another.
**Cost.** A turn that only generates text and calls no tool cannot be stopped from Tessera; it ends by itself shortly. Replay is built from what Tessera stored (events, per-minute samples, prompts, agents, policy decisions), so it has minute resolution for cost and does not replay model output, which Tessera never collects.

## 17. Spend history is a daily rollup per session, allocated at read time
**Choice.** A rollup writes each session's cost and tokens per UTC day from the per-minute samples (the rise across the day, measured from the last sample before it), every five minutes and on demand when the analytics page loads. Allocation (team, cost centre, person, repository, ticket, tag) is computed when read, from the session and its team.
**Why.** Samples are pruned after a month; spend history must last as long as the session. Keeping allocation out of the stored rows means changing a team's cost centre or the ticket pattern re-groups every past figure at once, the same way prices do.
**Cost.** A session that moves team keeps reporting under its current team for all its days. Days are UTC, so a team in another time zone sees a day boundary in its afternoon or evening. The forecast is a straight line from the last seven days' rate, and an unusual day is three standard deviations over the two weeks before it: both are prompts to look, not predictions.

## 18. The public API is the console's API; a key is its maker, narrowed
**Choice.** `/api/v1/*` is the console's own endpoints under a stable prefix, called with a bearer API key. A key carries no role of its own: it acts as the person who made it, with their role as it is now, limited to the scopes chosen, so demoting or disabling someone narrows or ends their keys within seconds. Keys are shown once and stored as a hash; actions taken with one are audited as "Name (API key label)". The CLI is a thin client over the same API and is served by each server, like the reporter.
**Why.** One implementation means the API cannot drift from what the console does, and every rule (who may act on which session, which policy version is current) applies to scripts unchanged. Tying a key to a person keeps "who did this" answerable without service accounts that outlive their owners.
**Cost.** There are no organisation-owned service accounts yet: a CI key belongs to a person and stops when they leave, which is deliberate but means a hand-over when it happens. GraphQL and generated SDKs from the plan are not built; the OpenAPI document is the contract they would be generated from.

## 19. A domain is proven with DNS before it routes anyone; SCIM manages people, not power
**Choice.** A domain added to single sign-on gets a token to publish as a TXT record at `_tessera-verify.<domain>`. Until the record is seen, the domain sends no sign-ins to the provider and creates no accounts. Any organisation may claim a domain, but only one can verify it, so an unverified claim blocks nobody. Domains configured before verification existed were marked verified by the migration. SCIM 2.0 creates, updates and deactivates people and turns groups into teams; it does not set roles, and it cannot deactivate an owner.
**Why.** Without proof of control, an owner could claim a domain they do not own and route its sign-ins to a provider they run. Roles decide who may approve tool calls and change policy; letting group membership at the provider grant them would move Tessera's most sensitive decision into a system whose admins are often a different team. Protecting owners keeps a provider mistake from locking an organisation out.
**Cost.** Grandfathered domains were trusted without a record; owners should re-check them. A person in several pushed groups lands in the team pushed last, because a Tessera user has one team. SAML is still not supported.

## 20. Data handling is enforced at the server edge, and the audit log is never rewritten
**Choice.** An organisation's data choices (metadata-only, data-loss classes, retention) are applied when a report arrives, before anything is stored, on top of the redaction the reporter already did. Data-loss classes are fixed, validated patterns (Luhn for cards, mod 97 for IBANs) plus literal terms; there are no user-written regular expressions in the ingest path. Retention runs per organisation and skips any organisation under legal hold. Erasure deletes a person's sessions and everything under them, their devices and keys, and replaces their name and email; audit entries stay. Audit streaming delivers entries in order, at least once, with their hashes.
**Why.** Filtering at the edge means a change takes effect on the next report and nothing sensitive reaches the database first. Validated patterns keep false positives (order numbers, build ids) out, and literal terms cannot make ingest slow. The audit log is the record of what was done, including erasures; rewriting it to remove a name would break its hash chain and its purpose, and GDPR allows keeping what is needed for that record.
**Cost.** Data-loss rules apply to new reports, not to what is already stored. The actor names in audit entries made before an erasure still read the person's name. Phone numbers and other national identifiers are not detected.

## 21. Other runtimes report through OpenTelemetry traces, folded into the same snapshot
**Choice.** `/api/ingest/otlp/v1/traces` accepts OTLP/HTTP JSON with the device token. Spans are folded per session into the snapshot a first-party reporter would send (agents from `invoke_agent` spans, tokens from `chat` spans, tool calls from `execute_tool` spans) and ingested through the same path, so pricing, budgets, policy decisions, analytics and the wall need nothing new. Because exporters send children before parents, attribution is recomputed from the whole span tree on each batch. Sessions are kept alive between spans and ended after five idle minutes. A session's cost is now its own usage plus every agent's, for every reporter.
**Why.** Every serious agent framework emits OpenTelemetry; meeting it there gives "any runtime, one console" without writing an adapter per runtime.
**Cost.** The accumulator is in memory: after a server restart, a long-running OTLP session restarts its totals from the next spans (the stored figures are kept, not added to). Protobuf encoding is not accepted. Traces are watch-only, since nothing on the machine asks Tessera before a tool call.

## 22. Replicas share the live fleet through Redis
**Choice.** Every change to a live session (a report, a pause, a stop, a hand-over, a removal) is published on Redis and applied by the other replicas, so each holds the whole live set and any replica can answer for any session. Browsers are told once, by the replica that made the change. A wait that started on one replica is closed out in Slack and PagerDuty by whichever replica sees it end. The Helm chart refuses a multi-replica install without Redis.
**Why.** Behind a load balancer a report and the answer to it land on different replicas; without a shared live set the answer would find no open prompt. Publishing the record keeps the hot path in memory, which is what made 500 sessions cheap.
**Cost.** Pub/sub is fire-and-forget: a replica that misses a message (a Redis blip) holds an older copy until that session's next report, about a second later. Delayed (escalation) notifications are scheduled by the replica that saw the wait begin; if it restarts, the notification log still stops anyone being told twice.

## 23. An approval shows the thing itself, flags risk deterministically, and can be remembered for the session
**Choice.** The reporter attaches to a prompt what the tool is about to do: the whole command, an edit's before and after, the first part of a whole-file write, the URL, the agent's last message before asking, the policy reason if Tessera forced the prompt, and the runtime's suggested allow rules. It also carries the last 40 tool calls with outcomes. Risk flags come from fixed, bounded patterns in the shared contract (no model, no network) and are computed wherever they are shown: the wall, the session page and the chat message. "Allow for the rest of this session" returns a session-scoped `updatedPermissions` entry to Claude Code; the rule is the runtime's own suggestion when it gives one, else a conservative prefix such as `Bash(pnpm test:*)` or the edited file's folder. Multiple-choice questions are caught in `PreToolUse` and answered through `updatedInput` when the console is quicker than the terminal.
**Why.** A one-line summary leaves an approver deciding blind, and blind approvals either rubber-stamp or stall. Showing the diff and the command, with what led there, is what makes a remote decision as informed as one at the terminal. A deterministic classifier is explainable and cannot be prompted into silence; it flags, it never decides. Session scope keeps a repeated approval from becoming a permanent rule nobody reviews.
**Cost.** Edits are capped at 6 000 characters each side and writes at their first 6 000; larger changes show a prefix. The flags know common tools and will miss an unusual one. Holding the `PreToolUse` hook open for a question delays the terminal dialog by up to 20 s (configurable as `questionWaitSeconds`), the same trade the permission wait already makes. Chat messages can only allow once.


## 24. The light theme remaps the dark tokens; preferences live in the browser
**Choice.** Every colour in the console is a Tailwind theme token, named for the dark palette (`ink` is the page, `snow` is the text). The light theme is one block in `styles.css`, `:root[data-theme="light"]`, that redefines those tokens: the neutrals invert and the accent 400s darken, so dark-on-accent text (primary buttons, "Allow once" chips) comes out light-on-dark. No class names change. Dark is the default; an inline script in `index.html` applies a saved light or system choice before the stylesheet paints, and the landing page is never under the attribute. Theme, navigation width and the wall's filter are per-browser preferences in `localStorage` under `tessera.`, through one `usePref` hook; nothing about them goes to the server.
**Why.** Remapping touched the stylesheet, nine hard-coded surfaces and nothing else, and is reversible in one commit; renaming tokens to roles would have rewritten every file for the same screen. Darkening the accents is what keeps the existing button and chip contrast without a second set of classes. A phone and a desk monitor legitimately want different widths and themes, so these are device settings, and keeping them out of the server keeps the preference surface from becoming an API.
**Cost.** A token's name no longer describes its colour under the light theme; the comment above the block says so. Preferences do not follow a person between browsers. The pre-paint script duplicates the resolution rule in `lib/theme.tsx` in four lines of plain JavaScript, so the two must be changed together.

## 25. The bell is a live list, not a log; acting on many sessions lets the server refuse each one
**Choice.** The bell shows what needs a person right now, derived in the browser from the live session list (waiting prompts, failed agents) plus the server's budget statuses. Nothing is stored or marked read: an item exists while the condition does and goes when it is dealt with. Acting on several selected sessions (pause, resume, message, stop) sends one request per session and reports how many the server refused and why; the refused ones stay selected. Keyboard answers on the wall (`a`, `d`) are offered only for permission prompts and plans, whose card already shows the command or diff with its risk; a question needs its options, so it opens the session.
**Why.** A control plane's alerts should agree with its wall (decision 10 keeps counts to one source); a separate notification store would drift from it and need read-state, retention and a second schema. Who may act on a session is decided server-side with the session's team and hand-over in view; duplicating that rule in the browser would be a second place to get it wrong, and an honest "3 of 5 done, 2 refused" is what an operator needs anyway. Answering from a card is as informed as answering from the session page only when the card shows the thing itself, which decision 23 made true for permissions and plans but not for a question's options.
**Cost.** There is no history of what needed attention or when; the audit log and session events hold what was done. A refused bulk action is reported once in a toast, not retried. Keyboard shortcuts are plain letters, so they are suppressed while typing in any field, and `?` and `/` need Shift on some layouts.

## 26. Hooks serialise through a lock, size their timeouts to the network, and degrade under a web filter rather than vanish
**Choice.** Each hook changes the session's state file under a per-session lock (a directory; mkdir is atomic everywhere), holds it only for the read-modify-write, never for the network, and takes over a lock older than 15 s. Request timeouts come from the measured round trip to the server (an EWMA kept per machine): 2.5× typical plus half a second, within bounds per call; the installed hook timeouts leave room for two round trips. A 403 whose body is an HTML page is treated as a web filter or WAF between the machine and the server, not as Tessera: the report is sent again with every free-text field reduced to its shape (tool names without arguments, event kinds without text, no command, diff or excerpt), tagged `network-filter`, and the session carries one note saying detail is withheld; a full report is tried again once a minute. A `decide` that is blocked is retried with only the program name. While a prompt waits for an answer, a failed poll is retried until the deadline instead of ending the wait. `doctor` reports the measured round trip and probes the filter with a command that looks like shell injection.
**Why.** Claude Code runs a hook per tool call and runs them concurrently for parallel calls; without the lock the last hook to save wins, so a PostToolUse closing a call was overwritten by a PreToolUse that loaded a moment earlier and the call stayed "running" for ever (37 of 40 on one machine). A fixed 1.5 s budget failed almost every call through a corporate proxy whose round trip is 1.5-2 s, so policy checks timed out (failing open) and most reports never arrived, and a session that reports nothing for 60 s falls off the wall. A content filter's signatures cannot be predicted, and a session whose last forty calls include one blocked command would otherwise be invisible for as long as that call stays in the window; showing it with detail withheld, and saying so, is both more useful and more honest than silence. Giving up on the first failed poll is what made an approval in the console arrive after the terminal had already asked.
**Cost.** A lock adds up to a few milliseconds per hook and, if a hook dies holding it, up to 15 s of delay for the next. Withheld reports lose the command and file detail an approver wants most; the `decide` fallback lets policy see the program but not its arguments, so a rule on arguments cannot match while the filter blocks them. The round-trip estimate is per machine, not per server. Budgets that follow a slow network can push a PreToolUse hook to several seconds per call on a bad link.

## 27. A session's health is a set of fixed rules over what the reporter already sends
**Choice.** The wall judges each live session with deterministic rules computed in the browser from the session view: the same tool failing three times in the last five calls (stuck), three policy denials in five (hitting policy), context at 80% (filling) or 90% (nearly full), two or more blowouts, a prompt waiting over ten minutes, thirty minutes and twenty tool calls with no change in the working tree (no progress), cost over $5 and three times the wall's median (outlier), two or more failed agents. The worst flag becomes a chip on the card with every flag's reason on hover, and "Needs a look" filters the wall to flagged sessions. A rule flags; nothing acts on it.
**Why.** "Running" and "waiting" say what a session is doing, not whether it is going well; a lead with forty cards needs the wall to point. Rules over data already on the card are explainable, cost nothing extra to send, stay identical wherever they are shown (decision 10's one-source principle), and cannot be prompted or drift. A model-scored health would be neither explainable nor cheap, and would invite acting on it.
**Cost.** Thresholds are fixed and will be wrong for some teams; they are constants in one file (`lib/health.ts`) and the chip always says which rule fired. "No progress" needs the reporter that sends files changed; older reporters never trigger it. The rules see only the last forty tool calls, so a session that was stuck an hour ago and recovered is "fine".

## 28. A waiting session stays on the wall: a per-session keep-alive on the machine
**Choice.** The first hook of a session starts a small detached process (`tessera-reporter keepalive <session> <claude-pid>`). Every 10 s it checks that Claude Code's process is still running and the session has not ended; if no hook has reported in the last 10 s, it sends the session's snapshot with `claimDeliveries: false`, so answers and messages stay queued for the hook that can act on them. It exits when Claude Code exits, the session ends, or another keep-alive owns the session.
**Why.** Hooks fire only when Claude Code does something. A session waiting at the terminal (a prompt nobody answered from Tessera in time, or idle between prompts) and a long tool call fire none, so they went silent after 15 s and left the wall after about 75 s: exactly the sessions a person needs to see. A detached process tied to Claude Code's own process needs no daemon, no service registration and nothing to clean up.
**Cost.** One extra Node process per open session, mostly asleep, and one report every 10 s while a session is quiet. A Claude Code that is killed outright leaves its session silent until it drops, as before.


## 29. A prompt is answerable in one place at a time, for a window the person chooses
**Choice.** The hook holds a prompt for Tessera for a window set by the owner's "where I answer" setting (at my desk: 10-15 s; either: the configured wait; away: up to 10 min, with hook timeouts installed at 660 s). The report carries `answerableUntil`; when it passes, the reporter marks the prompt `inTerminal` and Claude Code shows its own dialog. From then on the console shows "Now waiting in the terminal on <host>" with no answer buttons, and the server refuses a late answer with 409 rather than queueing it. Personal Web Push (VAPID keys kept in the database, no third-party account) sends waiting prompts with Allow/Deny actions, and a summary when a turn of 90 s or more ends or an agent fails; owners set to "at my desk" are not pushed. Prompts approved at least five times in 30 days, never denied, not high-risk and not covered by a rule are offered as one-click allow rules; an explicit allow rule lets the reporter skip Claude Code's prompt.
**Why.** Once Claude Code draws its dialog nothing outside the terminal can answer it, so an answer accepted by the console after that point was silently lost. Saying exactly where a prompt can be answered, and for how long, is the sync guarantee. Push is what makes "away" usable; the setting is per person because the same team mixes people at desks and people on phones.
**Cost.** Machines must re-run the installer to get the longer hook timeouts (`doctor` warns). iPhone push needs the site added to the Home Screen. An away-mode prompt blocks the terminal for up to 10 minutes unless answered in either place.

## 30. A mod inside Claude Code complements the hooks; it does not replace them
**Choice.** On Claude Code 2.1.287 and later the installer also installs the Tessera mod (`packages/mod-claude`), a plugin loaded in place from a marketplace directory at `~/.tessera/claude-plugins`. The settings hooks still report every event, run the policy check and hold prompts. The mod adds only what a hook cannot do: it long-polls the server for messages (`?kinds=message`, so it never takes an answer a waiting hook needs) and submits each as a prompt, which Claude Code starts at once on an idle session; `/tessera` shows the connection and sets away mode through `PUT /api/ingest/presence`; a band above the prompt shows when away mode is on; and it writes Claude Code's own context and cost figures to `~/.tessera/live/<session>.json`, which the hooks fold into their reports and mark with `reporter.features: ["mod"]`. Separately, a delivery that a report claims now waits in the session's inbox for the hook it is meant for, instead of being dropped when a tool hook's report happened to claim it.
**Why.** Hooks fire only when Claude Code does something, so a message to a session idle at its prompt waited for that session's next turn, and the console could only say "the next time it pauses". A mod runs in Claude Code's own process, can start a turn and can draw, which no hook can. Keeping the hooks as the reporting path means one code path for every Claude Code version, for `claude -p`, and for organisations whose managed settings allow only their own mods (`allowManagedModsOnly`): there the mod does not load and nothing else changes.
**Cost.** Two pieces on the machine instead of one, and they meet through a file: the mod's figures reach the server at the next hook or keep-alive report, up to 10 s later, and a file older than 90 s is ignored. The mod runs unsandboxed with the user's permissions, like any mod; `claude plugin validate` lists every call it makes, and it reads the device token only to send it to the server in a header. Its tests run only where Claude Code is installed (`claude plugin test`), so CI without Claude Code skips them and says so.

## 31. A diff is fetched when a person asks, and kept in memory, not stored
**Choice.** The console never receives code by default. Opening a changed file (or **Show diffs**) queues a `command` delivery `{ op: "diff" }` for the session; the reporter takes it with its next report (the keep-alive claims `claimKinds: ["command"]` only, so answers and messages stay for the hooks and the mod), runs `git diff HEAD` for the 40 biggest changes, redacts and caps it (20,000 characters a file, 200,000 in all) and posts it to `/api/ingest/sessions/:id/diff`. The server applies the organisation's DLP and keeps it in memory for 15 minutes. Only people who can act on the session may ask or read; every request is audited; metadata-only organisations and machines with excerpts off get none. The context fill is kept per minute (`samples.context_used`, the minute's highest reading) for the timeline, and the replay's playhead is a URL parameter.
**Why.** A diff is the most useful thing an approver or a lead can see and the most sensitive thing the machine holds. Asking on demand keeps it out of every report and every database backup, and an in-memory copy is enough for the minutes someone is looking. Reusing the delivery queue and the keep-alive's report means no new connection to the machine and no extra request while nobody asks.
**Cost.** A diff arrives up to about 10 s after the ask, longer behind a slow proxy. Behind several replicas it lives on the replica that received it, so a reader on another sees "ask again". A restart forgets every diff. A machine running a reporter from before this change never answers, and the console says so after a minute.

## 32. Spend alerts and the weekly digest come from the daily rollup and go out through the channels
**Choice.** A scheduler on every replica runs each quarter hour. For organisations that have a channel for them, it rolls up today and yesterday, checks each scope (the organisation, each team) for a day whose spend is more than three standard deviations above the two weeks before it and at least $5 above their mean (the rule Analytics already used to mark days, now in `fleet/spend.ts`), and on Monday from 08:00 UTC builds the digest of the week before. Both are ordinary notifications (`spend.anomaly`, `digest.weekly`) with a page to link to, so they reach Slack, Teams, PagerDuty and webhooks with no new delivery code, and the notification log's dedupe key (`anomaly:<scope>:<day>`, `digest:<ISO week>`) sends each once however many replicas run. Person and team pages read the same rollup, and Analytics groups carry the previous period's spend and the team's or person's id.
**Why.** The rollup is already the source of truth for spend, and channels already know how to reach people and record what they sent. A scheduler that only builds notifications keeps alerting and the digest consistent with what Analytics shows, and running it everywhere with a dedupe key avoids electing a leader.
**Cost.** The schedule is UTC: a team in Asia gets Monday's digest in its afternoon. The anomaly rule is fixed (no per-team thresholds), so a team with very spiky spend alerts less, and one with very steady spend more. There is no email: a deployment without Slack or Teams needs a webhook to its own mail relay.

## 33. "Explain this failure" is opt-in, server-side, and reads only the failure
**Choice.** A failed tool call or agent can be explained by a small Claude model (`EXPLAIN_MODEL`, Haiku by default). The server, not the browser, calls the Claude API with its own key (`ANTHROPIC_API_KEY`), so the key never reaches a page. The model reads what the reporter already sent for that failure (its summary and error output, redacted on the machine), the six calls before it and the repository name, with the organisation's DLP applied again; nothing else. It is off until an owner turns it on under Data and compliance, impossible in metadata-only mode, limited to people who can act on the session, capped per organisation per hour, cached for a day per failure and audited. Every number on the session page, Analytics, team pages and the summary card has a **?** that says how it is worked out, from one table of explanations (`lib/help.ts`).
**Why.** The error text is usually enough for a model to say what went wrong, and an approver reading `exit code 1` and twelve lines of a stack trace is exactly who benefits. Sending data to a model is a choice an organisation has to make knowingly, so the default is off and the toggle says what leaves. Explanations from one table keep the console from contradicting itself.
**Cost.** A Claude API key to manage and a small bill per explanation. The model reads only the last lines of output the reporter keeps, so a cause that scrolled away earlier is invisible to it; the answer says it can be wrong. Behind several replicas each keeps its own cache and its own hourly count.
